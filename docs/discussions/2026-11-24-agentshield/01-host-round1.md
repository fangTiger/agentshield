# 第 1 轮：主持人（Claude 主 Agent）的独立立场

> 本文写于看到另外两方意见之前，用于避免主持人只做汇总、没有自己的判断。

**Q1 范围**：基本同意现有分工，但要调整权重。
- 授权防线：作为主打。
- Skill 红线扫描器：作为第二亮点。它把官方的 6 条红线变成了工具，评委最有共鸣，技术上也最确定可行。
- 执行防线：只做最小版本。Agentic Wallet 自带代币安全审计，我们不重复造轮子，只做提示词注入特征匹配和恶意合约名单查询。

**Q2 授权防线的可行性**：这是最大风险，必须如实描述能力边界。
- 能做到的：
  - 解码二维码或链接，判断域名是否官方
  - 识别钓鱼话术
  - 查询免疫库
- 需要先实测的：用 `baw` 真实发起一次登录，抓取授权链接的格式。这是实现阶段的第 0 号任务。
- 关于「本机发起记录」：只有用户通过我们包装的登录入口发起时才可靠，所以只能作为辅助信号，不能当成卖点。

**Q3 ZK 层**：值得做，但要用成熟方案，不自己写电路。
- 用 Semaphore v4：链上维护 LeanIMT 增量 Merkle 树，用现成的 Groth16 验证器。在 BSC 上验证一次约 30 万 gas，按 0.12 gwei 计算大约 0.00004 BNB，成本可以忽略。
- 身份秘密由 Agent 在本地生成并保存。
- 持有者地址调用 `join(commitment)` 加入；合约检查 `balanceOf(msg.sender) > 0`，并且每个地址只能加入一次。丢失身份秘密时，可以由持有者地址发起更换。

**Q4 + Q5（关键）**：采用**双模式**，一次性解决两个冲突。
- **公开模式**：持有者地址直接上链举报或投票。这部分计入链上指标，信誉也沉淀到 `name.ai` 上。
- **匿名模式**：通过中继加 ZK 证明提交。不积累信誉，但仍然一人一票。适用于敏感场景，例如怕被诈骗团伙报复。
- 两种模式共用同一个 nullifier 空间，保证同一个真人对同一个威胁**无论用哪种模式都只能投一票**。实现上需要让公开投票也带上 nullifier：持有者在本地用自己的身份秘密算出 nullifier，随交易一起提交。合约无法验证这个 nullifier 是否算对，所以公开投票必须同样附上 ZK 证明，但由持有者地址自己发送交易。

**Q6 激励**：
- 核心价值是**保护自己**，这件事不需要激励。
- 举报的门槛做到最低：守卫拦截到可疑内容时，自动生成举报草稿，用户只需确认。
- 公开模式下给「首个发现者」和「守护者」徽章、排行榜。**不发钱**，避开「承诺收益」和「刷量」的嫌疑。

**Q7 攻击面**：
- 防假举报：至少 k 个不同真人确认，并经过一段冷静期，威胁才算生效；同时允许投「误报」票反驳；被举报的项目方可以通过证明自己控制合约部署者或域名来申诉。
- 防法律风险：措辞统一用「社区举报 N 次」，不说「已认定为诈骗」。
- **防投毒和注入**：链上只存结构化字段（类型、哈希、目标、证据 URI），Skill 绝不把举报里的自由文本拼进 LLM 提示词。

**Q8 演示**：
1. 打开一个伪造的「领取 Agent ID 空投，扫码验证」钓鱼页。
2. 用户问 Agent：「这个码能扫吗？」，Agent 红色拦截。
3. 用户一键匿名举报，生成 ZK 证明，网页实时显示「+1 真人确认」。
4. 第二个用户的 Agent 立即被拦截。
5. 用恶意 Skill 演示红线扫描，逐条标红违规点。

**Q9 最大盲点**：**用户用 App 扫码时，Agent 并不在流程里。** 用户必须先养成「扫之前问一下 Agent」的习惯，这个保护才生效。
- 补救方案：做一个轻量浏览器插件，在网页上检测非官方域名中出现的 Agentic Wallet 授权二维码，直接弹出警告。
- 也就是说，在网页这个最常见的投放场景，守卫要能主动出现，而不是等用户来问。
