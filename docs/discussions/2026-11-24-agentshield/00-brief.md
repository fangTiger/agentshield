- **安全红线**（违反任意一条直接取消资格）：

  6. 不得收集助记词、私钥、API Secret、配对码
- 其他限制：不得承诺收益；不得把 Agent ID 包装成「按名字查别人钱包」的工具；恶意刷量会被取消资格

## 2. 已核实的技术事实（2026-11-22 链上实测 + 官方文档）
- **Agent ID 合约**：`0x60b9262456de011f7d15a54cdd8c48baaa8b022f`
  - ERC-721，不可转让（有 `Soulbound()` 错误），一个 KYC 只能领一个
  - `tokenId = keccak256(handle)`
  - `ownerOfHandle(string) → address`，可以按名字查地址
  - `balanceOf(addr) > 0` 表示该地址持有 Agent ID
  - 事件 `Registered(bytes32 indexed tokenId, address indexed owner, string handle)`
  - **没有链上反向解析**（地址 → 名字），只能靠索引 Registered 事件
  - 没有 totalSupply；不是代理合约
- **铸造情况**：大约 2026-11-22 才开始，几小时内就有约 1,840 个，每小时 200–300 个。持有者大多是全新钱包（nonce≈1），余额约 0.0001 BNB；gas 价格约 0.12 gwei，BSC 出块约 0.45 秒
- **Agentic Wallet**（MPC 无私钥钱包，Agent 通过 `baw` CLI 加 Skill 来操作）：
  - 默认只能做白名单操作：swap、转账（只能转给 App 地址簿里的地址）、限价单、预测市场、DeFi
  - **调用任意合约需要用户在 App 内开启「开发者模式」**，然后执行 `baw contract-call preview` 和 `baw contract-call execute`（参数 --to、--inputData、--value(wei)），走独立的额度池
  - 签名只支持 EIP-712（同样需要开发者模式），**不支持 personal_sign / eth_sign**
  - 所有写操作都分两步：preview（模拟 + 风险检查）和 execute；部分操作需要在 App 内确认
  - 登录流程：Agent 生成链接或二维码 → 用户在 App 中核对 **6 位配对码**，并检查 OS/IP/地区 → 勾选 Secure Auto Sign 后确认。会话有最大时长和不活跃超时两种过期机制
  - 安全规则、地址簿只能在 App 里修改，Agent 只能读
- **未核实**：Agentic Wallet 授权二维码和深链接的具体格式；Skill 能否可靠地记录「本机发起的登录」；BNB Agent Studio 提到的 ERC-8004 registry 与 Agent ID 的关系

## 3. 当前产品构想：AgentShield + AgentZK
**一句话**：Agent 群体免疫系统。一个 Agent 识破骗局，全网 Agent 都会免疫。举报者通过零知识证明保持匿名，但一个真人（一个 Agent ID）只有一票。

**产品形态**：
1. **AgentShield Skill**：本地守卫，装在用户自己的 Agent 里
2. **BSC 合约**：链上免疫库，存威胁特征和匿名投票
3. **网页**：免疫库浏览、实时态势和统计

**三道防线**（按用户确认的优先级排列）：
1. **授权防线（主打）**：防扫码授权钓鱼和配对码钓鱼
   - 检测二维码或链接：是否官方域名、是否为 Agentic Wallet 授权请求、是否由本机自己发起
   - 配对码来源校验：Skill 记录本机发起过的登录；App 弹出配对码时，如果本机没有发起过登录，就提示用户拒绝
   - 话术识别：非官方来源出现「输入配对码」「扫码授权」之类的话术，判定为钓鱼
2. **供应链防线**：Skill 红线扫描器。安装第三方 Skill 前，按官方 6 条红线做静态扫描加 LLM 审查，扫描结果上链并接受社区匿名投票
3. **执行防线**：交易执行前检查提示词注入、恶意合约和蜜罐币

**AgentZK 匿名层**（Semaphore 式）：
- 每个 Agent ID 持有者在链上登记一个身份承诺（这一步由持有者地址直接调用合约，算作真实交互）
- 所有承诺组成一棵 Merkle 树
- 之后的举报和投票都附带 ZK 成员证明加 nullifier：合约能确认「是真人、没有重复投票」，但不知道是谁

**冷启动策略**：初始威胁数据由我们自己导入（公开钓鱼库、蜜罐检测、已知注入样本），第一个用户安装当天就能获得保护。

**我们自己必须守住红线**：绝不做扫码登录；只使用官方 `baw` 登录；不碰会话和配对码；合约开源并披露全部权限。

## 4. 需要讨论并达成一致的问题
请对下面每个问题给出明确立场（同意 / 反对 / 修改），并说明理由。

- **Q1 产品定位与范围**：三道防线都做，还是聚焦？主打授权防线是否站得住？哪些功能是评委看得到的亮点，哪些可以砍掉？
- **Q2 授权防线的真实可行性**：在拿不到官方二维码格式、也不能读取 App 会话的前提下，到底能检测什么？怎样避免产品「名不副实」？「本机发起记录」的方案是否可靠？
- **Q3 ZK 层是否值得做**：
  - 匿名带来的价值，是否大于它的复杂度和对用户理解的门槛？
  - 身份秘密存在哪里（Agent 本地）？如何与 Agent ID 地址绑定？
  - Merkle 树是在链上增量维护，还是链下计算后提交根？
  - 证明在哪里生成（Node 版 snarkjs 或 Noir）？谁来提交交易（中继）？
  - BSC 上验证一个证明的 gas 成本是多少？
- **Q4 匿名与链上指标的冲突**：匿名投票由中继提交，**交易发送方不是 Agent ID 地址**，可能不计入「30 个地址交互」和领航奖的统计。怎样设计，才能让持有者地址有足够多的真实交互，同时又不破坏匿名性？
- **Q5 匿名与信誉的冲突**：举报者匿名，信誉还能积累在 `name.ai` 上吗？要不要做匿名信誉，或者干脆放弃信誉？
- **Q6 激励**：用户为什么愿意举报、投票、开启开发者模式？要避免「承诺收益」和「刷量」的嫌疑。
- **Q7 攻击面**：
  - 骗子刷假举报，抹黑正规项目
  - 误报带来的法律或声誉风险
  - 免疫库本身被投毒
  - Skill 自身被注入
- **Q8 评委演示**：3 分钟的 demo，什么场景最打动评委？
- **Q9 你认为这个设计中最大的盲点，或者被高估的地方是什么？** 有没有更好的替代方案？
