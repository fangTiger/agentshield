# Round 2 — Claude 子 Agent

**D1 主打：折中，接受统一定位「Agentic Wallet 授权与信任守卫」。** 撤回我上一轮"把授权降为子功能"的意见。产品所有者明确要求做授权安全，而"安装 Skill 等于授权它动你的钱包"这个说法成立，两条线可以合成一个叙事。具体安排：
- 首页和 demo 的第一幕放授权体检，即 Codex 说的可见内容预警。
- Skill 红线扫描作为并列的第二支柱，链上证据最扎实。
- 两者共用同一个风险引擎和同一个链上信号库。

浏览器插件**首版不做**，原因有三：
- 授权链接格式还没核实，插件无从可靠识别；
- 钓鱼主要通过 TG 和 Discord 私信投放，网页只是其中一个渠道；
- 插件不用 Agent ID，也不产生链上交互，对占 30% 的「Agent ID 应用深度」评分没有贡献。

等第 0 号任务抓到链接格式之后再评估。

**D2 ZK 与信誉：提出更简单的统一方案。** 只保留一条投票路径：所有投票都附 ZK 证明和按议题隔离的 nullifier，区别只在**谁发送交易**：
- 持有者地址自己发送：即公开模式，计入链上指标；
- 中继发送：即匿名模式。

这样 nullifier 天然共享，合约只有一套校验逻辑，不需要"每个议题锁定一种模式"。代价是公开投票也要在本地生成证明，并且约 30 万 gas 由用户自付（新钱包只有 0.0001 BNB，大约够 2–3 次，需要提示）。这个代价我认为可以接受。

信誉方面**接受 Codex 的意见**：首版不把信誉绑到 `name.ai`，网页只显示"N 个真人确认"，同时避开"按名字查钱包"的红线。

**D3 不开开发者模式：我自己否定主路径，降为待测试的备选。**

已核实（官方 skills-reference 和 security 页面）：
- 转账的收款方必须在 App 通讯录里，通讯录只能在 App 内编辑；
- 自定义合约调用必须开启开发者模式，Agent 无法替用户开启；EIP-712 签名同样需要开发者模式。

未核实：
- 通讯录能否添加合约地址；
- 能否转 0 金额；
- 转账能否携带 calldata。

致命限制：即使走得通，`receive()` 也拿不到 calldata，所以只能记录"某地址加入了"，**无法提交身份承诺，也无法提交投票内容**。此外还有两个风险：转 BNB 给我们的合约容易被理解成"收钱"，需要在 `receive()` 里原路退回；preview 的风控也可能拦截收款方是合约的转账。

结论：核心交互必须走开发者模式。产品文案要如实说明开启它的用途，并建议用户把开发者模式的额度设为最低。转账触发 `receive()` 只作为"加入网络"的备选方式，第 0 天实测。

**D4 gas：接受。** 统一说法是"初步估算约 28.6 万 gas（第三方基准）+ 主网实测"。实测时分别报告证明验证、树插入和 calldata 三项成本。

**D5 叙事：接受 Codex 的意见，不再用"群体免疫"做主标语**，最多作为愿景出现一次。一句话定位：
> 「AgentShield：Agentic Wallet 的授权与信任守卫——扫码前、装 Skill 前先问它；每条风险信号由持有 Agent ID 的真人一人一票确认，可匿名、可申诉。」

## 我能接受的最终共识方案

产品统一定位为「Agentic Wallet 授权与信任守卫」，包括两个支柱：
- 授权体检：只分析用户提供的链接、二维码和话术，不宣称拦截，作为第一幕和主打；
- Skill 红线扫描：先跑静态规则，LLM 只能调高风险、不能调低。

两者共用一个链上风险信号库：
- 只能标"危险"，默认"待验证"，可以申诉；
- 投票统一用 Semaphore v4 证明加按议题的 nullifier，持有者可以自己发交易（公开，计入指标），也可以交给中继发送（匿名）；
- 首版不做个人信誉，也不做浏览器插件。

第 0 天先完成三项实测：抓取 `baw` 登录链接的格式、测量主网 gas、测试通讯录能否添加合约地址。同时向赛方确认"登记或投票交易计入 30 个地址的统计"的口径。
